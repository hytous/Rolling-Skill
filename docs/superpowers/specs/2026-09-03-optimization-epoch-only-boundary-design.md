# App 自动优化单一闭环 Epoch 边界设计

## 目标

App 的自动优化只让用户设置“最大闭环次数（Epoch）”。不再限制 Agent 在一个闭环内获得控制、调用 Tool、等待子任务结果或修正输出的次数，也不再让用户预估最长时间、Token、成本等内部消耗。

本设计只修改 Electron App，不修改 DSH 插件。它取代既有设计中针对新建自操作任务的 `maxIterations` 用户边界，以及自动优化的多维停止条件；旧任务仍需保持可读取和可恢复。

## 已确认的问题

当前自操作页面同时存在两套概念：

- “自动化边界”中的“最大迭代次数”按每次 Operator Runtime `startTurn` 计数，包括初始 Turn 和子任务结果回注后的 Turn。
- “停止条件与硬上限”中的“最大轮数”按完整优化 Epoch 计数。

两者不是一一对应关系。一个 Epoch 至少包括候选版本生成、实验安装、完整评测和结果分析，期间可能需要多个 Agent Turn。

当前实现还有更直接的错位：启动普通自操作任务时会提交 `maxIterations`，但启动自动优化时不会读取页面下方的 `maxIterations`。自动优化实际仍由 `maxEpochs`、`maxDurationMs`、`maxTurns`、Token、成本、耐心轮数和最小提升等旧字段控制。因此页面显示的“最大迭代次数”对自动优化没有实际作用。

## 选择的方案

采用“只限制完整闭环 Epoch”的方案：

- 用户只设置最大 Epoch 数。
- Agent 可以在一个 Epoch 内按实际需要进行任意次判断和 Tool 调用。
- Agent 可以在达到最大 Epoch 前主动判断优化已经完成。
- 用户可以随时手动停止。
- 达到最大 Epoch 后不再创建下一轮，但当前 Epoch 必须完成到可判断、可审批或可恢复的安全边界。

不保留“高级预算”入口，也不把旧字段折叠或隐藏后继续作为新任务的停止条件。

## Epoch 的准确定义

一个 Epoch 是一次完整、可比较的优化闭环：

```text
基于上一版与评测证据改进 Skill
  → 生成并冻结候选版本
  → 安装到所选实验 Runtime
  → 对冻结 Dataset 执行完整评测与 Judge
  → 对比 Baseline、上一轮和当前结果
  → Agent 决定结束或进入下一 Epoch
```

以下操作都不单独消耗 Epoch：

- Agent 在编辑候选版本时的多次思考、读取和 Tool 调用；
- 同一轮中多个 Case、多个目标 Runtime 和多个 Judge 执行；
- 子 Job 状态轮询、完成事件回注和结构化输出修复；
- 安装前检查、失败清理和可恢复重试。

只有开始生成下一份候选版本时，才进入新的 Epoch。

## 用户界面

自动优化配置中删除：

- “停止条件与硬上限”分组名称；
- 迭代模式（固定轮数/自适应）；
- 无提升容忍轮数；
- 最小有效提升；
- 最长时间；
- 操作 Agent 轮次；
- Token 上限；
- 成本上限；
- 目标分数；
- 目标通过率；
- “关键 Case 必须通过”用户开关。

“自动化边界”中删除“最大迭代次数”。普通自操作任务不再要求设置 Agent 操作次数；其结束条件是 Agent 完成、用户停止或技术故障。

自动优化只显示一个用户边界字段：

> 最大闭环次数（Epoch）

辅助说明为：

> 一轮包含：改进 Skill、安装候选版本、完整评测和结果复盘。闭环内的 Agent 操作次数不受限制。

该字段默认值为 5，只接受正整数，不再施加固定的 100 Epoch 产品上限。任务创建后冻结，Agent 不能在运行中扩大它。

## 调度与停止语义

### Agent 主动完成

每个 Epoch 的完整评测结束后，程序把 Baseline、上一轮和本轮的评分、通过率、失败项及回归项提供给 Agent。Agent 返回 `finish` 时，立即停止创建新 Epoch，并进入现有的一次最终审批。

不再由“达到目标分数”“连续提升不足”或“最小有效提升”替 Agent 作出完成决定。

### 达到最大 Epoch

当第 N 个 Epoch 完成且 N 等于用户设置的最大值时：

1. 不再请求第 N+1 个候选版本；
2. 固化第 N 轮完整评测和对比证据；
3. 进入一次最终审批；
4. 用户选择安装当前改进版或拒绝并恢复原版本。

最大 Epoch 只在完整闭环边界生效，不能在一轮编辑、安装或评测中途截断任务。

### 用户手动停止

用户可以在任何阶段点击停止。程序停止继续调度，并按现有恢复语义等待或收敛已经开始的副作用操作，随后恢复实验 Runtime 的原始 Skill 状态。手动停止不伪装成 Agent 正常完成，也不进入自动发布。

### 回归与不完整评测

删除用户可配置的质量阈值不等于允许无证据发布：

- Baseline 或当前 Epoch 的完整评测缺失时，不能把该 Epoch 计为可完成闭环，也不能进入发布审批；
- 新增关键失败、明显回归和安装恢复失败继续作为程序安全条件阻止自动发布；
- 最终审批必须展示 Baseline 与拟安装候选版本的完整对比，让用户决定安装或恢复原版本。

这些规则是结果完整性和防回归保护，不是需要用户预估的预算。

## Operator 与预算模型

新建普通自操作和自动优化 Operator Session 都不再携带用户 `maxIterations` 限制。自动优化的唯一计数由 Optimization Runner 持久化的 `currentEpoch` 与冻结的 `maxEpochs` 决定，而不是通过 Runtime Turn 数量间接换算。

新自动优化任务不再创建或执行以下预算：

- Runtime Turn 数量；
- 累计任务时长；
- Evaluation、Target 或 Judge 执行次数；
- Token 或成本；
- 预算扩容请求及其审批。

控制面仍按冻结的 Skill、Dataset、Repository 和 Runtime 范围授权操作。旧任务的七字段预算和现有 `maxIterations` 快照继续兼容读取、审计和恢复，但不会出现在新任务表单中。

## 技术故障保护

Runtime、子进程、IPC 和网络等待仍需内部看门狗，避免进程退出、连接丢失或永久无响应让任务无法恢复。这些保护满足以下约束：

- 不由用户配置；
- 不累计为任务“最长时间”；
- 不因为运行较久就把正常任务标记为完成或耗尽预算；
- 触发时进入明确的失败、暂停或恢复状态；
- 可恢复场景可以重连或继续，不申请用户扩大时间预算。

Agent 只有在正常获得控制时才能决定工作是否完成，因此不能用“交给 Agent 决定”替代进程失联检测。看门狗只判断系统是否仍可，不判断优化是否足够好。

## 数据流

```text
用户设置 maxEpochs
        ↓
冻结 Skill / Dataset / Rubric / Runtime / Baseline
        ↓
Baseline 完整评测
        ↓
┌─ Epoch N：改进 → 安装 → 完整评测 → 对比 → Agent 决策
│       ├─ Agent finish ─────────────────────────────┐
│       ├─ N == maxEpochs ───────────────────────────┤
│       └─ Agent continue 且 N < maxEpochs → Epoch N+1
└────────────────────────────────────────────────────┘
                                                     ↓
                                             一次最终审批
                                             ├─ 安装改进版
                                             └─ 拒绝并恢复原版
```

Runtime Turn、Tool 调用、Case 扇出和轮询只记录审计，不参与 Epoch 计数。

## 错误与恢复

- App 重启后从持久化的当前 Epoch 和阶段证据恢复，不能重复计数已完成 Epoch。
- 在候选生成、安装或评测中断时，恢复同一 Epoch，不因为重启新建 Epoch。
- 评测不完整时保留诊断证据并进入失败或可恢复状态，不消耗一个“成功闭环”后直接发布。
- 手动停止和程序故障均恢复实验安装，不能遗留候选版本污染目标 Runtime。
- 达到 Epoch 上限属于正常闭环结束，不标记为预算失败。

## 测试策略

### 配置与界面

- 新自动优化配置只要求正整数 `maxEpochs`，不再生成其他 limits、target 或 mode 字段。
- 页面不存在最大迭代次数、最长时间、Agent 轮次、Token、成本、耐心、最小提升和质量阈值输入。
- 页面清楚说明一个 Epoch 的组成以及闭环内部操作不限次。
- 普通自操作可以在没有 `maxIterations` 的情况下创建。

### 调度行为

- 一个 Epoch 内任意多个 Agent Turn 和 Tool Step 都不会触发停止。
- Agent 在上限前返回 `finish` 时进入最终审批。
- Agent 在第 `maxEpochs` 轮返回 `continue` 时仍不创建下一轮，而是进入最终审批。
- Epoch 上限不会中断已经开始的安装或完整评测。
- 运行时长不会触发优化停止或预算扩容审批。
- 用户手动停止可以从编辑、安装、评测和决策阶段安全收敛。

### 兼容与回归

- 旧 `maxIterations` 任务和旧七字段预算任务仍可读取与恢复。
- 新任务不创建 limit approval。
- 完整评测、回归保护、一次最终审批和拒绝后的恢复语义保持有效。
- Desktop 全量测试、Electron Renderer smoke、关键源码语法检查和 `git diff --check` 全部通过。

## 非目标

- 不修改 DSH 插件或 DSH 页面。
- 不删除底层卡死检测、进程退出检测和恢复机制。
- 不取消 Skill、Dataset、Repository 和 Runtime 的作用域限制。
- 不取消最终一次发布与安装审批。
