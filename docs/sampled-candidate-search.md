# 随机反馈多候选搜索：实现与使用

本功能是 Rolling Skill 的可选优化模式。它不依赖 AI 先为失败案例打“问题类型”标签，也不调用 NSGA-II；采用可复现随机反馈、完整回归、非支配排序和评分向量距离。

## 启用

在 Desktop 或 DSH 插件的优化设置中勾选“随机反馈多候选搜索”。不勾选时沿用旧的单线优化流程。UI 可以设置每组候选数、失败样本数、每 Runtime 并发 Case 数。

v3 优化请求可增加以下字段（与 skillId、Dataset、Runtime 等现有配置并列）：

```json
{
  "optimizationDirection": null,
  "limits": {"maxEpochs": 6},
  "search": {
    "candidatesPerRound": 3,
    "parentLimit": 2,
    "failureSamples": 6,
    "successSamples": 2,
    "feedbackCharacters": 12000,
    "caseWorkers": 1,
    "seed": "rolling-skill-v1"
  }
}
```

`search: {}` 使用上述搜索默认值；省略整个 search 则关闭新模式。配置随 Run 冻结并纳入摘要，运行中不可悄悄改变。

**maxEpochs 是候选总预算，不是搜索组数。** 上例最多生成、安装、全量评测 6 个候选，分为两组；外加一次完整基线评测。每组 3 个是所有父版本共享的总数，不是每个父版本各生成 3 个。

## 一组搜索如何运行

1. 在基线和此前已评测的历史候选中，程序选出最多 parentLimit 个活跃父版本。第一组只有基线。
2. 在本组固定的父版本池中轮流选择父版本。例如两个父版本 P、Q，3 个候选的父版本依次为 P、Q、P。组内新结果不会临时改变该组父池。
3. 将指定父版本的 Skill 文件恢复到本 Run 的独立 worktree，按候选种子抽取反馈，交给现有 Operator Agent 生成改进。
4. 提交不可变候选，在 Runtime 中安装，运行与基线相同的完整 Dataset × Runtime，再完成独立 Judge 评分。
5. 全部执行和评分结束后，才安装下一候选。达到总预算后由程序选择发布候选，仍需原有最终人工审批。

如果最佳版本仍是基线，则恢复初始安装状态并正常结束，不为了凑结果强行发布。同分同成本优先保留基线。最终审批界面展示的是选中候选，不一定是最后一轮候选。

## 随机抽样与上下文预算

- 抽样单位为 `(caseId, runtimeId)`，同一题在不同 Runtime 的表现可不同。
- 从执行、评分完成且具有有效正式得分的记录中，按现有评分的 pass/fail 划分通过与失败池，不增加语义分类模型。
- 默认每个候选最多抽 6 条失败、2 条通过作为防回归对照；全部通过时最多抽 8 条通过记录。池不足时取实际数量，不复制补齐。
- 候选内部无放回；候选之间允许重叠。用 `seed + runId + parentId + epoch` 派生种子，再按每条记录的 SHA-256 哈希排序取前 k 条。输入顺序变化不改变结果。
- 单次反馈卡片包含题目、回答摘要、低评分标准及说明、关键失败、被引用的少量 Trace 片段。标明截断与省略，不把未展示内容当成成功证据。
- 默认 12000 **字符**预算，并非精确 Token 预算。优先缩短证据，不静默删除已抽中的 Case；预算不足以容纳所有卡片时显式报错，提示减小抽样量或增大预算。
- 原始完整评测保留在 evaluation artifact；候选反馈另存 `optimization-feedback` artifact，保存种子、父版本、Case/Runtime ID，可审计和复现。

随机反馈提供不同观察子集，**不能保证 Agent 一定产生不同修改方向**。本版沿用现有 Operator 会话，不是每个候选建立全新模型会话；历史聊天仍可能影响后续生成。候选内容与已有版本完全相同时，现有不可变版本校验会拒绝提交并进入失败/恢复流程；尚未实现自动去重后重试。

## 前沿与评分向量

先执行资格检查：结果必须覆盖相同完整 Case × Runtime 集合，不能缺评分或仅有诊断性得分；平均质量不能低于基线；不能在任一道题上新增基线中没有的关键失败。

然后对合格版本做非支配排序：质量越高越好；平均执行耗时越低越好；若全部合格版本都有可靠 Token 计数，也加入平均 Token 越低越好的目标。某一成本轴存在缺失值时，整个轴不参与本次比较，绝不将未知成本视作零。

第一层是所有不被其他合格版本支配的版本；移除它们后再计算第二层，依次类推。层数由实际结果决定，不固定为“四层”。历史候选均保留在归档中，不只比较本组新候选，避免遗忘较早的优胜版本。

按层优先填充父池；同层有多个候选时，先选质量优先的代表，再贪心选择与已选父版本的最小距离最大的候选。第一层不足 parentLimit 时可以用后续层补齐；因此“两个活跃父版本”不等于“两个 Pareto 前沿”。

每个坐标是同一个 `(Case, Runtime, criterionId)` 的 0–10 分评分归一化到 0–1。只使用具有正权重、核验通过的普通评分项；自动失败和扣分规则不当成普通正向坐标。各 Case 内按标准权重归一化，Case/Runtime 之间等权。

```text
distance(A, B) = Σ w[j] × |scoreA[j] / 10 - scoreB[j] / 10| / Σ w[j]
```

只比较所有合格版本共同拥有、权重一致、已核验的坐标。共同坐标为空时距离为 0，退化为确定性排序，不把缺失证据算作多样性。无须让大模型再判断两份答案或 git diff 的语义相似度。

发布策略与父池策略分开：父池保留多样性；最终从第一层按质量、关键失败数、可用成本、稳定 ID 排序选一个，完全相同时优先基线。这里没有使用 NSGA-II 的拥挤距离、交叉算子或锦标赛，也没有实现互补收益 G 指标。

## 并发、隔离与版本清理

- `caseWorkers` 默认 1；确认隔离条件后可在 UI 调高至 2–8。上限按 Runtime 计算，两个 Runtime 各 3 Worker 就可能有 6 个执行客户端；Judge 仍是原有独立评分队列。
- 同一候选共享已安装的 Skill；不同 Worker 使用独立 Runtime 客户端，各 Case 使用 workspace 下 `.rolling-skill-evaluations/<run-hash>/<result-hash>` 工作目录。候选之间安装及完整评测严格串行。
- 本地工作目录隔离不等于数据库、远端 API 或外部文件隔离；有副作用的 Case 需自行提供隔离账号/数据。启用并发前还应确认 Runtime 能从子目录发现已安装 Skill、Case 不依赖固定相对目录。
- Case 工作目录可能含执行证据，因此不会自动强删。它们不是 Git worktree；目前没有自动保留期限策略。
- 每个 Run 只使用一个注册 worktree；不同逻辑父版本通过恢复 Skill 文件树切换，不为每个候选长期保留文件夹。Git 提交历史保持线性，逻辑父版本写在反馈和分析 artifact 中。
- 正常结束清理干净 worktree，保留候选提交、Run 分支引用和注册信息供追溯。不将落选候选 merge 回工作分支，不删除其 Git 对象。
- 有未提交修改时拒绝清理，报告保留原因；发布成功后的清理失败不会被误判成安装失败并触发回滚。安装恢复仍要求严格的目标摘要证明，无法证明时进入 needs_recovery，不盲目覆盖。

## 边界与验证

当前接入的是搜索控制和有界反馈机制，尚未贯通所有 Runtime 的真实 Token 遥测；生产评测中 Token 轴可能不可用。没有做真实账单数据集的端到端运行，不能据此声称质量提升或 Token/耗时下降。

主要实现：

- `desktop/rolling-skill/src/optimization/optimization-search.cjs`：抽样、前沿排序、评分向量距离。
- `optimization-runner.cjs`、`optimization-workspace.cjs`：多候选流程、父版本切换、选择与恢复。
- `optimization-agent-context.cjs`、`optimization-report.cjs`：有界反馈与审计报告。
- `desktop/rolling-skill/src/evaluation-runner.cjs`：有界 Case 并发与执行/评分完成屏障。

自动化测试覆盖抽样复现、无放回、上下文边界、共同评分坐标、完整回归资格检查、历史候选发布、基线保留、暂停恢复、并发等待、真实 Git 父版本恢复及安全清理。DSH 构建和 UI 请求链路也纳入验证。部分已有测试依赖 POSIX 0700 权限或创建符号链接权限，在当前 Windows 环境不能通过；没有为测试放宽相应安全约束。
